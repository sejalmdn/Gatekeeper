# Gatekeeper database schema

The Phase 1 schema is defined in
[`src/gatekeeper/persistence/schema.sql`](../src/gatekeeper/persistence/schema.sql). It organizes
each project's providers, model candidates, datasets, rules, run settings, and evaluation runs.

SQLite stores UUIDs and timestamps as `TEXT`. Application contracts are responsible for validating
UUID syntax and timestamp format. JSON columns are also stored as `TEXT`; database checks guarantee
valid JSON, while Pydantic contracts validate the structure required for each record type.

The current design treats datasets, candidates, and run settings as immutable after creation. It
does not include version, digest, or update-tracking fields. A changed model configuration,
dataset, or run policy is created as a new record.

## Relationship overview

```text
Project
├── Providers
│   └── Candidates
├── Datasets
│   ├── Scenarios
│   └── Rule bindings
├── Run settings
└── Evaluation runs
    ├── Candidate
    ├── Dataset
    └── Run settings
```

## `projects`

A project is the top-level workspace. All other records are scoped to a project either directly or
through a parent record.

| Field | Type | Required | Description |
|---|---|---:|---|
| `id` | `TEXT` | Yes | UUID primary key generated by Gatekeeper. |
| `name` | `TEXT` | Yes | Human-readable project name. Names are globally unique in the current schema. |
| `description` | `TEXT` | No | Optional explanation of the application or evaluation workspace. |
| `created_at` | `TEXT` | Yes | Timestamp recording when the project was created. |

## `providers`

A provider represents reusable access to a model service. It separates authentication and endpoint
details from the candidate configuration so several candidates can use the same provider account.

| Field | Type | Required | Description |
|---|---|---:|---|
| `id` | `TEXT` | Yes | UUID primary key generated by Gatekeeper. |
| `project_id` | `TEXT` | Yes | Project that owns the provider. References `projects.id`. |
| `name` | `TEXT` | Yes | User-facing name such as `Team OpenAI`. Unique within the project. |
| `provider_type` | `TEXT` | Yes | Supported identifier: `openai`, `anthropic`, `google`, `groq`, or `openrouter` for new connections. |
| `base_url` | `TEXT` | No | Optional provider API base URL, used for compatible or privately hosted endpoints. |
| `credential_ref` | `TEXT` | Yes | Reference to securely stored credentials. It must not contain or expose the API key itself. |
| `created_at` | `TEXT` | Yes | Timestamp recording when the provider was configured. |

`ix_providers_project_id` supports listing and resolving providers within a project. The composite
uniqueness of `(project_id, id)` allows child tables to enforce that related records belong to the
same project.

## `candidates`

A candidate is the immutable model configuration being evaluated. The system prompt, model,
available tool definitions, and generation options belong here rather than in scenario data.

| Field | Type | Required | Description |
|---|---|---:|---|
| `id` | `TEXT` | Yes | UUID primary key generated by Gatekeeper. |
| `project_id` | `TEXT` | Yes | Project that owns the candidate. References `projects.id`. |
| `provider_id` | `TEXT` | Yes | Provider used to invoke the model. The composite foreign key guarantees it belongs to the same project. |
| `name` | `TEXT` | Yes | User-facing candidate name. Unique within the project. |
| `adapter` | `TEXT` | Yes | Internal backend adapter selected from the provider type at creation; retained for existing candidates. |
| `model_name` | `TEXT` | Yes | Model identifier sent to the provider. |
| `system_prompt` | `TEXT` | Yes | System instructions supplied to the model. Defaults to an empty string. |
| `generation_parameters` | JSON `TEXT` | Yes | Provider generation options such as temperature, seed, or maximum output tokens. Defaults to `{}`. |
| `tool_definitions` | JSON `TEXT` | Yes | Tool schemas exposed to the model. Defaults to `[]`. Phase 1 observes tool requests but does not execute these tools. |
| `response_format` | JSON `TEXT` | No | Optional structured-output configuration supplied during model invocation. |
| `created_at` | `TEXT` | Yes | Timestamp recording when the candidate was created. |

`ix_candidates_project_id` supports project-scoped candidate listings. Candidate names are unique
within each project.

## `datasets`

A dataset groups the scenarios and rules used as evaluation input.

| Field | Type | Required | Description |
|---|---|---:|---|
| `id` | `TEXT` | Yes | UUID primary key generated by Gatekeeper. |
| `project_id` | `TEXT` | Yes | Project that owns the dataset. References `projects.id`. |
| `name` | `TEXT` | Yes | User-facing dataset name. Unique within the project. |
| `description` | `TEXT` | No | Optional explanation of the dataset's purpose. |
| `created_at` | `TEXT` | Yes | Timestamp recording when the dataset was created. |

`ix_datasets_project_id` supports project-scoped dataset listings. The composite uniqueness of
`(project_id, id)` lets evaluation runs enforce project ownership.

## `scenarios`

A scenario describes one controlled input to a candidate. Its `input` shape depends on the
scenario type and is validated by the corresponding Pydantic contract.

| Field | Type | Required | Description |
|---|---|---:|---|
| `id` | `TEXT` | Yes | UUID primary key generated by Gatekeeper. |
| `dataset_id` | `TEXT` | Yes | Dataset containing the scenario. References `datasets.id`. |
| `scenario_key` | `TEXT` | Yes | Stable, user-facing identifier used within the dataset. Unique within that dataset. |
| `name` | `TEXT` | Yes | Human-readable scenario name. |
| `scenario_type` | `TEXT` | Yes | One of `single_turn`, `multi_turn`, or `tool_use`. |
| `input` | JSON `TEXT` | Yes | Type-specific model input. Private expectations and rules are deliberately excluded. |
| `created_at` | `TEXT` | Yes | Timestamp recording when the scenario was created. |

Typical `input` objects are:

```json
{"user_message": "What is 2 + 2?"}
```

```json
{
  "history": [
    {"role": "user", "content": "My order is 123."},
    {"role": "assistant", "content": "How can I help?"}
  ],
  "user_message": "Where is it?"
}
```

`ix_scenarios_dataset_id` supports loading all scenarios for a dataset. The composite uniqueness
of `(dataset_id, id)` prevents a scenario rule from referring to a scenario in another dataset.

## `rule_bindings`

A rule binding configures a supported evaluator for a dataset or scenario. Gatekeeper implements
the evaluator identified by `rule_type`; the row provides its private expected values and settings.

When `scenario_id` is null, the binding is a dataset default and `applies_to` selects compatible
scenario types. When `scenario_id` is present, the binding applies only to that scenario and
`applies_to` must be null. A scenario binding with the same `rule_key` as an applicable dataset
default replaces that default when Gatekeeper assembles the effective rules.

| Field | Type | Required | Description |
|---|---|---:|---|
| `id` | `TEXT` | Yes | UUID primary key for this binding row. |
| `dataset_id` | `TEXT` | Yes | Dataset that owns the binding. References `datasets.id`. |
| `scenario_id` | `TEXT` | No | Scenario receiving the rule. Null means the rule is a dataset-level default. |
| `rule_key` | `TEXT` | Yes | Logical identifier used to distinguish rules and match scenario overrides to defaults. |
| `rule_type` | `TEXT` | Yes | Supported evaluator type, such as `response.regex`, `tool.selection`, or `judge.rubric`. |
| `role` | `TEXT` | Yes | Result behavior: `required`, `scored`, or `informational`. |
| `severity` | `TEXT` | Yes | Fixed importance category: `critical`, `high`, `medium`, or `low`. |
| `parameters` | JSON `TEXT` | Yes | Rule-specific settings and private expected values, such as a regex, accepted answers, tool name, JSON Schema, limit, or judge criterion. |
| `applies_to` | JSON `TEXT` | Conditional | Scenario-type array for a dataset default. Required for defaults and prohibited for scenario-specific rules. |
| `created_at` | `TEXT` | Yes | Timestamp recording when the rule binding was created. |

The two partial unique indexes enforce unique `rule_key` values within dataset-default scope and
within each scenario. The dataset and scenario indexes support effective-rule assembly.

Rule roles have these effects:

- `required`: a failed rule causes the scenario attempt to fail.
- `scored`: the result contributes to aggregate scoring without independently failing the attempt.
- `informational`: the result is reported but does not affect pass/fail or scoring.

Severity has a fixed product-wide relative weight for scored rules: `critical` is `4`, `high` is
`3`, `medium` is `2`, and `low` is `1`. These values express relative importance; they are not
user-configurable run settings. Required rules still control pass/fail independently of weight, and
informational rules remain unweighted.

## `run_settings`

Run settings define how Gatekeeper executes and aggregates an evaluation. Scenario-specific
expectations do not belong here; they remain in rule bindings.

| Field | Type | Required | Description |
|---|---|---:|---|
| `id` | `TEXT` | Yes | UUID primary key generated by Gatekeeper. |
| `project_id` | `TEXT` | Yes | Project that owns the settings. References `projects.id`. |
| `name` | `TEXT` | Yes | User-facing settings name. Unique within the project. |
| `attempts_per_scenario` | `INTEGER` | Yes | Number of independent attempts to execute for each scenario. Must be positive. |
| `timeout_ms` | `INTEGER` | Yes | Maximum duration of one candidate attempt in milliseconds. Must be positive. |
| `pass_threshold` | `REAL` | Yes | Required aggregate passing fraction, between `0.0` and `1.0`. |
| `created_at` | `TEXT` | Yes | Timestamp recording when the run settings were created. |

The LLM judge is configured once by the Gatekeeper deployment and cannot be selected through run
settings. `ix_run_settings_project_id` supports project-scoped settings listings.

## `evaluation_runs`

An evaluation run combines one candidate, one dataset, and one run-settings record. Composite
foreign keys prevent resources from different projects from being combined.

| Field | Type | Required | Description |
|---|---|---:|---|
| `id` | `TEXT` | Yes | UUID primary key generated by Gatekeeper. |
| `project_id` | `TEXT` | Yes | Project that owns the run. References `projects.id`. |
| `candidate_id` | `TEXT` | Yes | Candidate invoked by the run. Must belong to the same project. |
| `dataset_id` | `TEXT` | Yes | Dataset evaluated by the run. Must belong to the same project. |
| `run_settings_id` | `TEXT` | Yes | Execution and scoring settings used by the run. Must belong to the same project. |
| `status` | `TEXT` | Yes | Lifecycle state: `pending`, `running`, `completed`, or `failed`. Defaults to `pending`. |
| `created_at` | `TEXT` | Yes | Timestamp recording when the run was created. |
| `started_at` | `TEXT` | No | Timestamp recording when execution began. |
| `completed_at` | `TEXT` | No | Timestamp recording when execution reached a terminal state. |

`ix_evaluation_runs_project_id` supports project-scoped run listings. Attempt-level execution
evidence and rule results will require additional tables when that part of Phase 1 is implemented.
